1. Мета й постановка задачі

Реалізувати та опублікувати HTTP API служби доставки на Cloudflare Workers Free з Google Cloud Firestore Spark, перевірити захист запису та дослідити витрату квоти читань при offset- і курсорній пагінації.

Мова: JavaScript. Початковий набір: 30 посилок і 60 подій. Розмір сторінки: 25. Cache-Control: max-age=300.

2. Реалізація та модель даних

Колекція parcels містить tracking, weight_kg (0.01–1000), city, status (прийнято, в дорозі, доставлено, повернено), created_on (дата), fragile (boolean), cod_amount (0–500000). Кожен документ має підколекцію events з at (UTC), location, note. Ідентифікатори призначає Firestore, належність події задається шляхом.

GET/POST /api/parcels, GET /api/parcels/:id, GET/POST /api/parcels/:id/events, GET /api/parcels/stats?day=YYYY-MM-DD. Коди: 200, 201, 400, 401, 404, 405, 413, 415, 503. Список потребує status та city, підтримує limit і offset. Зміни PUT/PATCH/DELETE не підтримуються згідно з прикладом методички.

Запит 1: стан і місто, weight_kg DESC, id DESC. Запит 2: сума cod_amount для status=доставлено та created_on=day; порожня сума дорівнює 0. «За день» тлумачиться за created_on: окремої дати вручення в схемі немає. Запит 3: усі events заданої посилки, at DESC та id DESC.

Складені індекси: (status ASC, city ASC, weight_kg DESC, __name__ DESC); (status ASC, created_on ASC, cod_amount ASC). Конфігурація наведена у firestore.indexes.json. Поля перевіряються до звернення до БД.

3. Хід роботи та перевірки

Запити приймає мережа Cloudflare. cf-ray ідентифікує запит, суфікс вказує центр обробки. max-age=300 дозволяє кешувати GET 200 до п’яти хвилин, тому після запису можлива застаріла відповідь. Cache API не використовується; наявність Cache-Control сама по собі не доводить edge-кешування.

Читання API публічне. Окремої автентифікації користувачів, обмеження частоти запитів і гарантовано сталого за часом порівняння Bearer-токена немає. Безперервні читання можуть вичерпати безкоштовну квоту та зробити API тимчасово недоступним. Роль сервісного акаунта діє в межах проєкту, тому для лабораторної використовується окремий проєкт.

4.4. Витрата квоти

x-read-count списку отримується з Query Explain executionStats.readOperations при analyze=true. Це реальне вимірювання виконання, яке також витрачає квоту. Пропущені через offset документи оплачуються. Курсор використовує значення маси та id останнього елемента, без попереднього GET документа.

СпосібСторінкаПовернутоx-read-countfloor(50000 / reads)
offset1[вимір][вимір][розрахунок]
offset2[вимір][вимір][розрахунок]
cursor1[вимір][вимір][розрахунок]
cursor2[вимір][вимір][розрахунок]

Вставити вивід scripts/measure.mjs. Наведена формула дає межу за одним ресурсом для повторень саме такого запиту, без інших операцій, консолі та лімітів Worker. При оплаті враховуються ті самі операції; остаточна ціна залежить від регіону й індексних читань. Очікуваний ефект курсора описати після фактичного вимірювання.

Додаток. Використання мовної моделі

Для підготовки структури проєкту, коду, тестів та цього шаблону використано Codex. Автор роботи має самостійно перевірити розгортання, зібрати фактичні виміри й пояснити реалізацію.
